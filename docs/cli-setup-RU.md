# Claude Code CLI — подробная настройка режима /Project

Дополнение к `START-HERE.md`. Здесь то, что нужно один раз понять, а не то, что
нужно сделать за пять шагов.

## 1. Что откуда берётся

| Слой | Файл | Кто читает | Что решает |
|---|---|---|---|
| Контракт режима | `<ws>/CLAUDE.md` | сессия, каждый раз | режим, ранги, что запрещено всегда |
| Пол разрешений | `<ws>/.claude/settings.json` | CLI, до вызова инструмента | какие вызовы вообще возможны |
| Контур проекта | `Project_*/.ai-loop/policy/*.yaml` | `classify_diff.py` | риск изменения по фактическому диффу |
| Память проекта | `Project_*/.ai-loop/context.md` | фазы цикла | установленные факты, команды, иерархия истины |
| Журнал | `Project_*/.ai-loop/ledger.jsonl` | `ledger.py`, аудит | что классифицировано, кем одобрено, под какой policy |

Первые два — про **вызовы инструментов**. Третий — про **содержимое диффа**. Это
разные поверхности: сессия без плагина теряет хуки, но не теряет
`settings.json`; изменение, пришедшее скриптом мимо permission-слоя, всё равно
встречает классификатор.

## 2. Порядок разрешений — то, на чём легко ошибиться

```
deny  ->  ask  ->  allow      первое совпадение выигрывает
```

Специфичность **не** меняет порядок. Узкое `allow` не перебивает широкое `deny`.
`deny` на любом уровне настроек (managed / project / user) не переоткрывается
другим уровнем.

Практическое следствие, ради которого это здесь: односегментные `deny`-шаблоны
совпадают **на любой глубине**. `Edit(.ai-loop/policy/**)` закрывает и
`<ws>/.ai-loop/policy/`, и `Project_x/.ai-loop/policy/`, и любую вложенную
глубже. Для `allow` это не так — там путь привязан к указанному уровню.

`Edit(...)` покрывает Write, NotebookEdit и MultiEdit. Отдельные правила для них
не нужны, и правило с именем инструмента без пути CLI не подсвечивает.

Синтаксис между версиями CLI дрейфовал. Перед тем как полагаться на профиль —
сделайте пробную правку в закрытый путь и убедитесь, что получили именно тот
ответ, которого ждали.

## 3. Цепочка policy

`classify_diff.py` собирает **все** policy от истинного корня файловой системы
вниз через репозиторий:

```
слои-предки над --repo   ->  собственная policy репозитория  ->  вложенные policy
```

Каждый слой, который управляет путём, классифицирует его; берётся максимальный
риск. Вложенная policy может только ужесточать.

Посмотреть, что реально нашлось:

```bash
python3 Project_<имя>/.ai-loop/bin/classify_diff.py --repo Project_<имя> --self-check
```

Поле `policy_chain` — это и есть цепочка. Если в ней слой, о котором вы не
знали, разберитесь **до** первого прогона: внешний слой поднимает риск, и вы
получите гейты там, где их не ждали, без очевидной причины.

`--no-chain` классифицирует только по policy указанного репозитория. Это
диагностика. В CI ей не место.

## 4. Команды цикла

Проверено на реальном прогоне — сигнатуры взяты из `--help`, не по памяти.

```bash
P=Project_<имя>
B=$P/.ai-loop/bin

# идея передаётся ПОЗИЦИОННО, не через --idea
python3 $B/loop.py --repo $P start "идея одной строкой" --actor "Имя Фамилия"
# -> {"run_id": "20260815-204940-ideya-odnoy-strokoy", ...}

python3 $B/loop.py --repo $P status
python3 $B/loop.py --repo $P enter    --run-id <id> --phase PLAN
python3 $B/loop.py --repo $P gate     --run-id <id> --phase BUILD --cumulative
python3 $B/loop.py --repo $P complete --run-id <id> --phase PLAN --artifact <path>
python3 $B/loop.py --repo $P approve  --run-id <id> --actor "Имя Фамилия"
python3 $B/loop.py --repo $P finish   --run-id <id> --commit <sha>

python3 $B/ledger.py --repo $P verify        # целостность хеш-цепочки
```

`--run-id` обязателен везде, кроме `start` и `status`. `--actor` принимается и до,
и после подкоманды.

`--actor` принимается и до, и после подкоманды. `--actor agent` на `approve`
отклоняется — это и есть разделение «предлагающий ≠ оценивающий».

`--cumulative` пересчитывает объединение всего, что прогон трогал, а не только
текущий шаг. Это защита от серии по отдельности разрешённых патчей, которые
вместе меняют то, что policy запретила бы одним куском.

## 5. Что делает `/Project` режим свободнее

Не «меньше проверок». В Agent-режиме над каждым изменением висит вопрос «не
ослабляет ли это мой собственный control plane?» — и любое касание policy
безусловно CRITICAL. При работе над чужим модулем этот вопрос неприменим: там
нет вашей policy, которую можно ослабить.

Убирается не защита, а **неприменимая** защита. Рабочим вопросом становится
вопрос проекта: «не ломает ли это его инварианты?» — и отвечает на него policy
проекта.

Отсюда жёсткое предусловие: **без заполненного контура проекта это не «свободный
режим», а «режим без гейтов»**. Пока зоны TODO, всё unmatched, то есть CRITICAL —
цикл встанет на всём, и это правильное направление отказа.

## 6. Коннекторы (MCP)

`.mcp.json` в плагине объявляет подключения. Правило, которое стоит держать в
голове: **skill без коннектора — это просто промпт**. Пока GitHub-коннектор не
подключён, «открой PR» останется текстом о том, как открыть PR.

Минимум для этого режима — доступ к форджу проекта (GitHub / GitLab). Трекер
задач полезен, но не обязателен.

## 7. Триггеры

Запуск без человека — расписание, вебхук репозитория, API. Настраивается скиллом
`loop-triggers`, шаблоны в `templates/triggers/`.

Порядок внедрения, который стоит соблюдать: сначала прогоны, чей результат
человек смотрит перед применением (draft PR, черновик), и только потом —
автономные действия. Обратный порядок обнаруживается по тому, что одобрения
начинают ставиться не глядя.

## 8. Разбор частых ошибок

| Симптом | Причина | Что делать |
|---|---|---|
| `no policy directory found` | запуск не из того корня | добавить `--repo Project_<имя>` |
| всё CRITICAL, `unmatched_path` | зоны в шаблоне ещё TODO | `/ai-loop:control-plane-init`, зоны утверждает человек |
| `--self-check`: «nested policy ... may not lower an outer floor» | вложенная policy мягче внешней | привести вложенную в соответствие; цепочка её всё равно переопределит |
| `unrecognized arguments: --actor` | старая копия `loop.py` | перевендорить: скопировать `scripts/*.py` в `.ai-loop/bin/` |
| гейт срабатывает на каждой мелочи | `.ai-loop/context.md` не в зоне E | добавить его и `.ai-loop/memory/` в зону E |
| хук не блокирует вложенную policy | старая копия хука | обновить плагин; проверка стала глубино-чувствительной |
| `Zip file contains path with invalid characters` | не-ASCII имя внутри архива | пересобрать `zip -X`; `validate_plugin.sh` это проверяет |
| правки в `Tool/` проходят молча | их и не должно быть в этом режиме | это не работа /Project-режима; вынести отдельно |

## 9. Проверка, что контур действительно работает

Не «настроен», а работает — разные состояния, и разница не видна, пока что-нибудь
не должно было сработать и не сработало.

```bash
P=Project_<имя>

# 1. классификатор видит дифф
echo "// probe" >> $P/<файл из зоны E>
python3 $P/.ai-loop/bin/classify_diff.py --repo $P --explain

# 2. защищённый путь действительно поднимает риск
python3 $P/.ai-loop/bin/classify_diff.py --repo $P \
  --paths .ai-loop/policy/protected_paths.yaml --explain    # ждём CRITICAL

# 3. цепочка видна
python3 $P/.ai-loop/bin/classify_diff.py --repo $P --self-check | grep -A5 policy_chain

# 4. журнал целостен
python3 $P/.ai-loop/bin/ledger.py --repo $P verify
```

Если пункт 2 вернул не CRITICAL — контур декоративен, и всё, что он до этого
«одобрил», проверено не было.
