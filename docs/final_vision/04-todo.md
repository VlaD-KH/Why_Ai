# 04 — Матрица задач и критерии приёмки

Формат совпадает с корневым `todo.md`. Каждая задача содержит **проверяемый**
критерий приёмки и зону/риск — чтобы гейт был предсказан заранее, а не обнаружен
в момент коммита.

Легенда риска: определяется `.ai-loop/bin/classify_diff.py`, не мнением агента.

---

## Класс сложности задачи (для подбора модели)

Ось, независимая от зоны/риска (та решает, кто утверждает коммит; эта —
какая модель должна писать код). Два класса:

- 🟢 **Мелкая/монотонная** — механическая правка по известному шаблону
  (константы, ENV, экранирование, тесты по шаблону, замена одного
  эндпоинта на другой). Годится модель с меньшим ризонингом и большими
  лимитами — reasoning не является узким местом.
- 🔴 **Сложная/последовательная** — многошаговый reasoning, конфликтующие
  инварианты, архитектурное решение (протокол переподключения, fail-closed
  граница безопасности, крипто-валидация). Требует модель с ризонингом,
  ошибка здесь не механическая, а логическая.

## Правило атомарности коммитов (важно перед началом)

Совокупная классификация показала неочевидное: **даже два разрешённых файла в
одном коммите требуют человека.** Пара `Eye/*.html` + `tests/test_*.py` даёт
эскалацию `test_and_product_same_diff`: MEDIUM → HIGH → `require_human`.

Из этого следуют два правила:

1. **Один шаг плана = один коммит = одна семантическая причина.**
2. **Тесты и код, который они проверяют, — в разных коммитах.** Сначала падающий
   тест (зона T), затем реализация. Это и требование политики, и способ соблюсти
   Proof of Falsification.

## Фаза 1 — Реальная доставка и авторизация

### TASK-TG-01: Реальный HTTPS-транспорт
**Файл:** `Tool/connectors/telegram_connector.py` · **Зона R · CRITICAL · require_human**
**Класс:** 🟢 мелкая/монотонная — известный паттерн `urllib.request.urlopen` с таймаутом

- *Критерий:* `send_alert` выполняет реальный `POST /sendMessage` через
  `urllib.request`; при недоступности API возвращает `delivered: False` с причиной.
- *Критерий:* ни одного стороннего импорта — `httpx`/`requests` не появляются.
- *Критерий:* таймаут задан явно; истечение таймаута не роняет процесс.
- *Анти-критерий:* не должно остаться пути, возвращающего `delivered: True` без
  фактической отправки. Сейчас **весь** метод такой.

### TASK-TG-02: Чтение секретов из окружения
**Файл:** `Tool/connectors/telegram_connector.py` · **Зона R · CRITICAL**
**Класс:** 🟢 мелкая/монотонная — `os.getenv`, один параметр

- *Критерий:* токен читается `os.getenv(self.bot_token_env)`; сейчас `os` не
  импортирован, а имя переменной только сохраняется в атрибут.
- *Критерий:* при отсутствии токена — явная ошибка в логе и `delivered: False`,
  а не молчаливый успех.
- *Критерий:* токен **никогда** не попадает в лог, в возвращаемый словарь и в текст сообщения.

### TASK-TG-03: Авторизация операторов (наивысший приоритет фазы)
**Файл:** `Tool/connectors/telegram_connector.py` · **Зона R · CRITICAL**
**Класс:** 🔴 сложная/последовательная — граница безопасности fail-closed;
ошибка в крайних случаях (пустой список, отсутствующий ENV) даёт тихий bypass

- *Критерий:* `handle_incoming_command` принимает `user_id`; сейчас параметра нет вообще.
- *Критерий:* список операторов из ENV (`WHY_AI_TELEGRAM_OPERATORS`), НЕ из репозитория.
- *Критерий:* **fail-closed** — пустой/незаданный список отклоняет всё, включая `/panic`.
- *Критерий:* отказ пишется в лог с указанием `user_id`.
- *Критерий:* ID оператора отсутствует в любом отслеживаемом git-файле
  (проверка: `git grep <id>` → пусто).

### TASK-TG-04: Экранирование MarkdownV2
**Файл:** `Tool/connectors/telegram_connector.py` · **Зона R · CRITICAL**
**Класс:** 🟢 мелкая/монотонная — таблица спецсимволов из документации Telegram

- *Критерий:* сообщение, содержащее `_ * [ ] ( ) ~ \` > # + - = | { } . !`,
  доставляется без ошибки Telegram API.
- *Критерий:* тест проверяет **результат экранирования**, а не факт вызова функции.

### TASK-TG-05: Устранить протухшие счётчики
**Файлы:** `Tool/connectors/telegram_connector.py:99` (R), `Core/server.py:120` (R)
**Класс:** 🟢 мелкая/монотонная — заменить литерал на фактический подсчёт

- *Критерий:* `52/52 PASS` и `32/32 PASS` заменены на фактический подсчёт.
  На момент аудита в репозитории **76** тестов — обе константы лгут.

### TASK-TG-06: Тесты фазы 1
**Файл:** `tests/test_telegram_connector.py` (новый) · **Зона T · MEDIUM**
**Класс:** 🟢 мелкая/монотонная — тесты по шаблону на уже описанные критерии

- *Критерий:* каждый тест **наблюдался падающим** до реализации (фиксация в отчёте).
- *Критерий покрытия:* успешная доставка · отказ транспорта · отсутствие токена ·
  отказ авторизации · авторизация пустым списком · экранирование.
- *Анти-критерий:* ни один тест не должен проходить против заглушки, возвращающей
  константу. Это основной дефект существующего `tests/test_mcp_connectors.py`.

### TASK-TG-09: Входящие команды через long polling

### TASK-TG-10: `/panic` с проверкой результата ⚠️
**Файл:** `Tool/connectors/telegram_bridge.py` · **Зона R · CRITICAL**
**Класс:** 🔴 сложная/последовательная — уже один раз сделана неверно
в исходной спецификации (ложный "остановлено" на 404); критична не механика,
а инвариант "молчание/ошибка ≠ успех"

- *Критерий:* вызывается `POST /api/panic` — **реальный** маршрут. Маршрутов
  `/api/control/panic` и `/api/mcp/*` в `Core/server.py` не существует.
- *Критерий:* **HTTP-статус проверяется обязательно.**
- *Критерий (главный):* при не-2xx оператор получает сообщение об **отказе**.
  Спецификация здесь сообщала «Инициируется Exit Code 10» при 404 в ответ —
  оператор считал систему остановленной, когда она работала.
- *Тест:* подменить эндпоинт на несуществующий → мост обязан сообщить об отказе.

### TASK-TG-11: `/status` через правильный эндпоинт
**Файл:** `Tool/connectors/telegram_bridge.py` · **Зона R · CRITICAL**
**Класс:** 🟢 мелкая/монотонная — заменить один эндпоинт на другой

### TASK-TG-12: Расхождение пути `failures.jsonl`
**Файл:** `Core/server.py:332` · **Зона R · CRITICAL**

### TASK-TG-07b (найдено при реализации TG-07/08, не начато): файловые источники алертов
**Файл:** `Tool/connectors/telegram_bridge.py` · **Зона R · CRITICAL**
**Класс:** 🔴 сложная/последовательная — три разных источника, разная семантика опроса

Мост (TASK-TG-07/08) подписан на `GET /api/events/stream` и умеет фильтровать
по серьёзности, но реально через SSE вещается только `panic_stop` (→ `crit`).
Из четырёх уровней старой спецификации (`PANIC`/`CRITICAL`/`CONSENSUS`/`SIZE_WARN`)
три остаются неподключёнными:

- *Критерий:* `CRITICAL` (падение тестов) — источник `Core/failures.jsonl`,
  опрос/tail файла, не SSE.
- *Критерий:* `CONSENSUS` (вето кворума) — возвращаемое значение
  `QuorumReviewer.review_diff()`, вызывать снаружи, не встраивать в
  `Supervisor/`.
- *Критерий:* `SIZE_WARN` (храповики) — `antigravity_debug.log`
  (`launcher.py` пишет туда через `FileHandler`), tail лога.
- *Анти-критерий:* ни один из трёх не подключать через правку `Supervisor/`
  — тот же принцип, что уже действует для `panic_stop` (docs/final_vision/02-architecture.md).

## Проверка перед каждым коммитом

```bash
python .ai-loop/bin/classify_diff.py --repo . --self-check    # ok: true
python .ai-loop/bin/classify_diff.py --repo . --worktree      # предсказать гейт
python -m unittest discover -s tests -p "test_*.py"           # зелёно
python run_mvp.py --self-test                                 # exit 0
```

`--worktree` (а не `--paths`) — важно: в режиме `--paths` порог
`lines_changed_over` **структурно не может сработать**, `collect_paths()`
жёстко возвращает `lines_changed = 0`. Объём изменений виден только в
`--worktree` / `--staged` / `--range`.
