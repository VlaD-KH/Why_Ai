# ai-loop — установка и использование

Плагин запускает цикл реализации из одной команды:

```
/start_Ai добавить rate limiting в публичный API
```

Дальше он сам ведёт работу по этапам `GROUND → CONTROL → DEFINE → PLAN → BUILD →
VERIFY → REVIEW → SHIP`, классифицируя каждое изменение по фактическому `git diff`
и останавливаясь на человеке там, где изменение не заслужило автономии.

Плагин **не привязан к предметной области**. Карта зон строится из вашего
репозитория при первой настройке — осмотром дерева и вопросами о том, что ломать
нельзя, — а не из шаблона «как обычно бывает».

---

## 1. Что нужно

| | |
|---|---|
| Claude Code CLI | `npm install -g @anthropic-ai/claude-code` |
| Python 3.8+ | только стандартная библиотека, ставить нечего |
| git | обязателен: авторитет классификации — `git diff --name-only` |
| `gh` (опционально) | для `/ai-loop`-этапа SHIP, чтобы открывать PR |

Внешние MCP-коннекторы **не требуются**. Контур защиты работает на `git` и Python —
специально: страховка, которая перестаёт работать при недоступном коннекторе, это не
страховка, а зависимость в форме страховки, и отказывает она ровно тогда, когда нужна.

## 2. Установка в Claude Code CLI

### Вариант A — локальный marketplace (рекомендуется)

Распакуйте архив плагина, например в `~/plugins/ai-loop`, затем:

```bash
claude plugin marketplace add ~/plugins/ai-loop
claude plugin install ai-loop@ai-loop-marketplace
```

Проверка — обязательно `claude plugin list` перед `/help`, а не вместо него:

```bash
claude plugin list
```

Должно быть `Status: enabled`. Если написано `failed to load` — плагин не
зарегистрировал вообще ничего: ни команды, ни скиллы, ни хуки, и `/help` это
никак не покажет, просто список будет короче на весь ai-loop. Обычная причина —
битый JSON в `.claude-plugin/` или неверная форма `hooks/hooks.json` (нужен
`{"hooks": {...}}` целиком, а не голая карта событий); версии ≥0.1.3 несут это
исправленным.

Только после `enabled`:

```bash
claude
> /help          # в списке должны быть /start_Ai, /ai-status, /ai-gate,
                 # /ai-approve, /ai-control-plane
```

### Вариант B — git-репозиторий

Положите каталог плагина в свой git-репозиторий и подключите его по URL:

```bash
claude plugin marketplace add https://github.com/<вы>/<repo>
claude plugin install ai-loop@ai-loop-marketplace
```

Так удобнее для команды и обязательно для CI: в шаблоне
`templates/triggers/github-dispatch.yml` есть переменная `AI_LOOP_PLUGIN_REPO`.
**Закрепляйте версию тегом или коммитом** — неприкреплённый плагин означает, что
правила могут поменяться между запусками, и ни в одном диффе этого не будет видно.

### Вариант C — Cowork (десктоп)

Файл `ai-loop.plugin` перетащить в чат Cowork и нажать кнопку установки. Скиллы будут
доступны как `/ai-loop:<имя>`, а роутер `ai-loop-router` подхватывает запросы
обычным текстом, без команд.

### Обновление и удаление

```bash
claude plugin marketplace update ai-loop-marketplace
claude plugin uninstall ai-loop
```

## 3. Первая настройка в проекте

Делается **один раз на репозиторий**. Порядок важен и не произволен.

```bash
cd /путь/к/проекту
claude
```

```
> /ai-control-plane init
```

Что произойдёт:

1. **Сбор контекста** — плагин осмотрит дерево, прочитает README/CI/манифесты и
   задаст до пяти вопросов. Главный: **что здесь нельзя сломать?** Из ответа
   выводится зона R; без него зона R — догадка.
2. **Вывод зон из реального дерева.** Каждый путь проверяется на существование.
   Путь, которого нет, ничего не защищает, но выглядит так, будто защищает.
3. **Черновики файлов**: `.ai-loop/policy/*.yaml`, `CODEOWNERS`,
   `.github/workflows/ai-loop-enforcement.yml`, плюс копия классификатора в
   `.ai-loop/bin/`.
4. **Проверка, что контур что-то запрещает** — путь вне зон и сам файл policy
   должны дать `CRITICAL`.

Дальше **вы** проверяете диффы и коммитите. Плагин не коммитит правила, под которыми
работает: агент, способный переписать свои ограничения, ограничений не имеет.

### Что нужно включить руками (в GitHub, не в репозитории)

```
Settings → Branches → защита ветки по умолчанию:
  ☑ Require a pull request before merging
  ☑ Require review from Code Owners
  ☑ Restrict who can push
  ☑ Required status check: «ai-loop enforcement»
  ☐ merge-права боту/автоматизации — НЕ давать
```

Это единственный барьер, который живёт **вне** сессии агента. `CODEOWNERS` без защиты
ветки — это комментарий: в ревью выглядит как enforcement, в проде ведёт себя как
пожелание.

### Проверить, что всё сошлось

```
> /ai-control-plane check
```

Должно быть: `--self-check` проходит, путь вне зон → `CRITICAL`, `.ai-loop/policy/…`
→ `CRITICAL`, реальный путь зоны E → `LOW`. Если третий тоже блокируется — зона E
пустая или перекрыта более широким защищённым шаблоном; чините сразу, иначе автономно
не сможет делаться ничего, а классификация перестанет что-либо сообщать.

### Аудит перед первым автономным запуском

```
> /ai-control-plane review
```

Ищет обходы: алиасы путей, самоссылочность, последовательности разрешённых патчей,
которые в сумме дают запрещённое состояние. Отдельным проходом — потому что тот, кто
писал черновик, найдёт в нём ровно те возражения, о которых подумал сам.

## 4. Обычная работа

```
> /start_Ai добавить экспорт отчёта в CSV
```

Дальше плагин ведёт этап за этапом. Что делать вам:

| Команда | Когда |
|---|---|
| `/start_Ai <идея>` | начать прогон |
| `/ai-status` | «что вообще происходит», что заблокировано |
| `/ai-gate <run-id> <ФАЗА>` | классифицировать текущий дифф вручную |
| `/ai-approve <run-id> approve "<причина>"` | снять блокировку |
| `/ai-control-plane check` | быстрая проверка контура |

Роутер понимает и обычный текст — «продолжи вчерашнее», «на каком этапе»,
«почему остановился», «отревьюй перед мержем».

### Когда прогон остановился

Это не сбой. Классификатор посчитал, что изменение затрагивает пути, которые
требуют решения человека.

Вам покажут: что делает изменение, какие пути подняли уровень, что сломается, если
изменение неверно. Дальше:

```bash
python3 .ai-loop/bin/loop.py approve --run-id <id> --actor вася --note "посмотрел дифф, ок"
python3 .ai-loop/bin/loop.py reject  --run-id <id> --actor вася --note "спека неверная"
```

`--actor` должен быть человеком — `agent` команда отклоняет. Это механическая форма
правила «предлагающий не утверждает».

**Не работает и работать не должно:** перезапуск с более узким набором путей, дробление
диффа ради цифры пониже, правка policy, чтобы изменение прошло. Все три — способы
поспорить с классификатором, а он ровно та часть системы, которая не торгуется.

### Уровни риска

| Риск | Автономия | Проверка | Человек |
|---|---|---|---|
| LOW | продолжает | критерий приёмки проверен | не нужен |
| MEDIUM | продолжает | критерий проверен **и** тест показан падающим до того, как прошёл | выборочно постфактум |
| HIGH | только предложить | полная верификация до предложения | обязателен, поимённо |
| CRITICAL | никогда | — | обычный человеческий процесс |

Сверх уровня «по путям» есть эскалации: тесты в одном диффе с кодом, любое касание
policy-плоскости, путь вне зон, слишком большой дифф — и **накопительная** сумма
прогона: серия дешёвых по отдельности шагов не должна складываться в изменение,
которое policy отказала бы принять целиком.

## 5. Запуск без вас (триггеры)

```
> настрой запуск по расписанию
```

Три вида: расписание, событие репозитория (webhook), API-вызов. Шаблоны — в
`templates/triggers/`.

Правила для любого автономного прогона:

- `AI_LOOP_UNATTENDED=1` — этапы не задают вопросов, которые некому услышать
- останавливаться на **draft PR**, никогда не мержить
- гейт всё равно останавливает: уровень риска — свойство изменения, а не того, кто
  сидит за клавиатурой
- у аккаунта автоматизации **нет** прав на merge

**Начинайте со скучного.** Вариант B в `templates/triggers/scheduled-run.md` —
проверка дрейфа: читает контур, проверяет журнал и в нормальный день выводит одну
строку. Стоит копейки и доказывает, что обвязка триггера работает, до того как от неё
что-то зависит. Именно обвязка отказывает первой, а не модель.

И главный вопрос перед настройкой: **кто читает результат и когда?** Триггер, который
каждую ночь кладёт PR в репозиторий, где утром никто не смотрит, не автоматизировал
работу, а передвинул очередь. Пропускная способность ревью, а не генерации, определяет,
сколько этого имеет смысл запускать.

## 6. Как добавлять свои скиллы

Все скиллы лежат в **`SKILLS/`** — по одному плоскому файлу, имя файла описывает
функцию. Каталог `skills/<имя>/SKILL.md`, который нужен загрузчику, **генерируется**:

```bash
python3 scripts/build_skills.py           # пересобрать skills/ из SKILLS/
python3 scripts/build_skills.py --check   # проверить, ничего не записывая
bash    scripts/validate_plugin.sh        # полная структурная проверка
```

Порядок для нового скилла:

1. `SKILLS/<что-делает>.md` — имя файла по функции (`verify-falsify-tests.md`,
   а не `skill7.md`).
2. Во frontmatter: `name` (нижний регистр, дефисы — это адрес, по которому его
   вызывают) и `description` с триггер-фразами **на английском и на русском**.
3. Строку в `SKILLS/00-INDEX.md` и маршрут в `SKILLS/router-intent-front-door.md`.
4. `python3 scripts/build_skills.py && bash scripts/validate_plugin.sh`

Двуязычные триггеры — не украшение. Описание только с английскими фразами означает,
что для русскоязычного запроса скилла не существует: он не сматчится, и никто об этом
не сообщит. `validate_plugin.sh` валит сборку, если русских фраз нет.

**Никогда не правьте `skills/` руками** — следующая сборка перезапишет молча, и от
изменения не останется даже диффа. Полная конвенция — в
`SKILLS/authoring-add-a-new-skill.md`.

Отдельно: **enforcement никогда не живёт в скилле.** Скилл — это промпт, а промпт не
является границей безопасности: с ним можно поспорить, он теряется в контексте, и
ничто не сообщает, когда он не был выполнен. Всё, что должно держаться независимо от
выводов модели, идёт в `scripts/` и в CI.

## 7. Что появится в вашем репозитории

```
.ai-loop/
├── context.md          память проекта, читается в начале каждого этапа
├── policy/             карта зон + матрица риска — ваши, коммитит человек
├── bin/                копия классификатора, чтобы CI не зависел от плагина
├── ledger.jsonl        хеш-цепочка: что классифицировано, кем одобрено
└── runs/<run-id>/      spec.md, plan.md, verification.md, review.md
CODEOWNERS
.github/workflows/ai-loop-enforcement.yml
```

Журнал `ledger.jsonl` не ротировать, не чистить, не переформатировать — любое из
этого рвёт цепочку и уничтожает ровно то свойство, ради которого он ведётся.
Проверка: `python3 .ai-loop/bin/ledger.py verify`.

## 8. Если что-то не так

| Симптом | Что это | Что делать |
|---|---|---|
| всё подряд `CRITICAL` | контур не создан либо зоны пустые | `/ai-control-plane init`, заполнить зону E |
| `--self-check` падает | policy читается строже, чем принуждает | исправить перечисленные свойства до запуска |
| `no policy directory found` | нет `.ai-loop/policy/` | `/ai-control-plane init` |
| гейт срабатывает в середине плана | сработало накопительное правило | приземлить сделанное и начать новый прогон |
| хук не сработал | хуки настроены не во всех средах | не считать «настроен» и «срабатывает» одним и тем же; проверить в интерактивной сессии и записать факт в `context.md` |
| `git push` → `could not read Username` | в песочнице нет учётных данных | коммиты уже локально, запушить из своего терминала |
| `ledger verify` → `ok: false` | записи меняли после написания | это не проблема форматирования; смотреть историю git по `ledger.jsonl` |

## 9. Чего плагин не делает

Не мержит. Не пушит в защищённую ветку. Не утверждает свою же работу (`approve`
отклоняет `--actor agent`). Не правит policy-плоскость. Не понижает риск, чтобы
пройти гейт. Не сообщает результат теста, которого не наблюдал.

Это не настройки. Это причина, по которой всему остальному вообще можно давать
автономию.

## 10. Честные ограничения

- **Хук — не граница.** `PreToolUse`-guard работает внутри сессии, которую сторожит,
  и намеренно падает «открыто». Граница — обязательный status check на защищённой
  ветке. Пропустите этот шаг — получите полезную договорённость, а не enforcement.
- **Журнал фиксирует, что решение приняли, а не что его обдумали.** Если одобрения
  приходят через секунды после классификаций — гейт стал штампом, и лечится это
  меньшим числом гейтов на низкорисковых путях, а не призывами к дисциплине.
- **Настоящий предел — пропускная способность ревью.** Время, сэкономленное на
  написании кода, возвращается временем на его аудит. Это стоит закладывать в план,
  а не обнаруживать.
